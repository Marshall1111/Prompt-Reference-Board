# 后台任务记录分页与检索设计

## 背景

当前后台“任务记录”页通过 `GET /api/image-jobs` 拉取最近一批任务后直接在前端渲染。

现状问题：

- 接口默认只返回最近 80 条任务，最大也只支持 200 条
- 前端没有分页能力
- 搜索能力缺失，无法快速定位历史任务
- “已加入卡夹”的任务虽然有 `isLiked` / `likedAt` 字段，但不能单独筛出

这会导致任务变多以后，较早的任务虽然仍然保存在 `data/image-jobs/` 中，但在后台页面里会被更新的任务“挤掉”，无法直接找到。

## 目标

本次改造要让后台任务记录页支持真正的历史查询能力，满足以下目标：

- 后端任务列表接口支持分页
- 后端任务列表接口支持组合筛选
- 前端任务记录页支持翻页查看历史任务
- 前端任务记录页支持关键词搜索
- 前端任务记录页支持按单天日期筛选
- 前端任务记录页支持“仅看卡夹”筛选
- 保留现有状态筛选、查看、下载、修改、删除、加入/移出卡夹等操作

## 非目标

本次不做以下内容：

- 不修改小程序任务页的查询逻辑
- 不修改公开玩法观测面板的展示与轮询逻辑
- 不新增全文索引、数据库存储或专门的搜索引擎
- 不支持按日期范围搜索，只支持按单天筛选
- 不支持多条件高级检索语法

## 现状梳理

### 后端

当前 `GET /api/image-jobs` 的行为是：

- 读取 `data/image-jobs/` 下全部任务
- 按 `createdAt` 倒序排序
- 截取前 `limit` 条
- 返回 `jobs`

缺少：

- `page`
- `total`
- 关键词搜索
- 日期筛选
- `likedOnly`
- 服务端状态筛选

### 前端

当前后台 `ImageJobsPage`：

- 初始化时拉取 `/api/image-jobs`
- 每 2 秒轮询一次同一接口
- 在前端只做状态筛选
- 不支持搜索、日期、分页

同时页面里还有一个独立的“公开玩法观测”区域，该区域数据来自 `/api/admin/draw-card-sessions`，和任务记录列表是两套数据源。

本次任务记录分页与检索只作用于“任务记录列表”，不改变“公开玩法观测”的现有逻辑。

## 方案概览

采用“后端分页 + 后端筛选 + 前端参数驱动列表”的方案。

### 推荐原因

- 能查询全部历史任务，而不是只在最近 80/200 条里过滤
- 服务端先筛选后分页，结果稳定
- 前端状态更简单，避免在浏览器里处理大量任务对象
- 后续如果任务量继续增长，也更容易继续迁移到数据库或索引方案

## 接口设计

继续复用现有接口：

- `GET /api/image-jobs`

返回结构从仅有 `jobs` 扩展为包含分页信息：

```json
{
  "jobs": [],
  "total": 0,
  "page": 1,
  "limit": 20
}
```

### 查询参数

接口新增并支持以下查询参数：

- `page`
  说明：页码，从 1 开始
- `limit`
  说明：每页条数
- `status`
  说明：任务状态，取值为 `all`、`queued`、`running`、`partial`、`succeeded`、`failed`、`cancelled`
- `search`
  说明：关键词搜索
- `date`
  说明：按单天筛选，格式为 `YYYY-MM-DD`
- `likedOnly`
  说明：仅看卡夹，取值为 `true` 或 `false`

### 默认值

- `page` 默认 `1`
- `limit` 默认 `20`
- `limit` 最大 `100`
- `status` 默认 `all`
- `search` 默认空字符串
- `date` 默认空字符串
- `likedOnly` 默认 `false`

### 服务端筛选顺序

后端处理顺序如下：

1. 读取全部任务
2. 按 `status` 筛选
3. 按 `likedOnly` 筛选
4. 按 `date` 筛选
5. 按 `search` 筛选
6. 按 `createdAt` 倒序排序
7. 计算 `total`
8. 根据 `page` 和 `limit` 截取当页数据

这个顺序保证前端看到的总数和分页结果一致。

## 搜索规则

`search` 统一做不区分大小写的包含匹配，匹配以下字段：

- `jobId`
- `prompt`
- `styleName`
- `styleGroupName`

说明：

- 对字符串字段统一转成安全字符串后再比较
- `search` 为空时，不进行关键词过滤

## 日期筛选规则

### 输入格式

`date` 必须是 `YYYY-MM-DD` 格式。

非法日期值直接返回 `400`。

### 匹配语义

日期筛选按任务 `createdAt` 所属自然日匹配。

示例：

- `date=2026-06-07`

表示筛选出所有 `createdAt` 落在以下范围内的任务：

- `2026-06-07 00:00:00.000`
- 到 `2026-06-07 23:59:59.999`

### 时区

统一使用服务器本地时区进行“自然日”换算。

原因：

- 后台日期输入和服务器实际筛选结果保持一致
- 与当前项目中其他按日期管理数据的行为更一致

## “仅看卡夹”定义

“仅看卡夹”筛选基于任务记录已有字段：

- `isLiked === true`

当 `likedOnly=true` 时，只返回已加入卡夹的任务。

说明：

- 不区分公开玩法任务和后台手动任务
- 只要任务记录本身处于 `isLiked === true`，就属于筛选结果

## 状态筛选规则

状态筛选复用现有任务状态值：

- `queued`
- `running`
- `partial`
- `succeeded`
- `failed`
- `cancelled`

当 `status=all` 时，不进行状态过滤。

## 前端页面设计

目标页面：

- 后台 `ImageJobsPage`

### 新增筛选控件

在任务记录区域新增一组查询控件：

- 关键词输入框
- 日期选择器
- “仅看卡夹”开关或复选框
- 查询按钮
- 重置按钮

说明：

- 关键词输入框用于搜索 `jobId`、提示词、风格名、风格组名
- 日期选择器用于按单天筛选
- “仅看卡夹”用于过滤 `isLiked` 任务
- 状态筛选按钮组继续保留

### 查询状态

前端维护以下查询状态：

- `page`
- `limit`
- `status`
- `search`
- `date`
- `likedOnly`

当以下条件变化时，自动重置到第一页：

- `status`
- `search`
- `date`
- `likedOnly`

这样可以避免筛选条件变化后仍停留在旧页码，造成“当前页无数据”的困惑。

### 分页控件

任务列表底部新增分页控件，至少包含：

- 上一页
- 下一页
- 当前页 / 总页数
- 任务总数

规则：

- 首页禁用“上一页”
- 最后一页禁用“下一页”
- 如果 `total` 为 0，则隐藏或禁用分页动作

### 刷新行为

保留“刷新”按钮。

点击刷新时，使用当前查询条件重新请求当前页数据。

### 轮询行为

当前页面每 2 秒轮询一次任务列表。分页引入后，轮询保留，但行为调整为：

- 使用当前查询条件轮询当前页
- 不重置筛选条件
- 不强制跳回第一页

这能保持“正在处理中”的任务自动刷新，同时不打断管理员正在查看的历史页。

### 空状态

当查询结果为空时，文案继续使用：

- “还没有符合条件的生图任务。”

这个文案已经能覆盖“没有任务”和“筛选无结果”两种场景。

## 前端交互细节

### 推荐的查询提交流程

为避免每次输入一个字符都触发请求，关键词搜索采用“受控输入 + 显式提交”：

- 输入关键词
- 点击“查询”后发起请求

日期和“仅看卡夹”也与查询按钮一起提交。

状态筛选按钮可继续保留即时生效体验，但即时切换时也应重置到第一页。

### 重置行为

点击“重置”后恢复默认查询条件：

- `page=1`
- `limit=20`
- `status=all`
- `search=""`
- `date=""`
- `likedOnly=false`

然后立即重新拉取列表。

## 接口返回兼容性

后台任务页会改为读取：

- `jobs`
- `total`
- `page`
- `limit`

现有只读取 `jobs` 的调用方在本项目中主要是后台任务页和小程序任务页。

兼容策略：

- 返回结构继续保留 `jobs`
- 小程序仍然只读取 `jobs`
- 新增的 `total/page/limit` 不会破坏旧调用方

## 错误处理

### 后端

以下情况返回 `400`：

- `page` 非法
- `limit` 非法
- `status` 不在允许范围内
- `date` 格式非法

其他异常返回 `500`，继续沿用：

- “读取生图任务列表失败。”

### 前端

后台任务页请求失败时：

- 保留现有错误展示区域
- 不清空用户当前输入的查询条件

这样管理员修正条件或重新点击刷新即可继续操作。

## 测试要点

### 后端

- 默认请求返回第一页 20 条，并包含 `total/page/limit/jobs`
- `status` 能正确筛选各状态任务
- `likedOnly=true` 只返回 `isLiked` 任务
- `search` 能匹配 `jobId`、`prompt`、`styleName`、`styleGroupName`
- `date=YYYY-MM-DD` 只返回该自然日任务
- 多个筛选条件叠加时结果正确
- 分页在筛选后进行，而不是筛选前

### 前端

- 页面初始加载显示第一页
- 切换状态筛选会回到第一页
- 输入关键词并点击查询后，列表正确刷新
- 选择日期并查询后，列表正确刷新
- 打开“仅看卡夹”后，只显示已加入卡夹的任务
- 上一页 / 下一页切换正确
- 刷新按钮会保留当前查询条件
- 轮询不会打断当前页和当前筛选状态

## 实现步骤

1. 扩展后端 `GET /api/image-jobs` 查询参数解析与返回结构
2. 抽出任务筛选与分页逻辑，避免路由函数过长
3. 扩展前端 `refreshImageJobs` 支持传入查询参数
4. 改造 `ImageJobsPage`，加入查询状态与分页状态
5. 在任务页新增关键词、日期、“仅看卡夹”和分页控件
6. 调整轮询逻辑，使其基于当前查询条件刷新
7. 自测组合筛选与翻页场景

## 风险与取舍

### 风险一：任务量继续增长后，后端每次仍要扫描所有 JSON

这是当前文件存储模型下的固有成本，但本次先接受。

原因：

- 当前任务规模下实现成本最低
- 能快速解决“历史任务查不到”的实际问题
- 如果后续任务规模显著增长，再考虑迁移数据库索引

### 风险二：轮询历史页的意义较弱

当管理员正在看较老页码时，轮询大多数时候不会有变化。

本次仍保留轮询，原因是：

- 能保持当前页面行为一致
- 管理员切回第一页时，无需额外恢复实时刷新

如果后续觉得噪声较大，可以进一步优化为“仅第一页或有进行中任务时轮询”。

## 最终决策

本次采用以下最终方案：

- 复用 `GET /api/image-jobs`
- 由后端提供分页与筛选
- 搜索字段包含 `jobId`、`prompt`、`styleName`、`styleGroupName`
- 增加按 `createdAt` 的单天日期筛选
- 增加“仅看卡夹”筛选
- 后台任务页改为基于查询参数的服务端分页列表
- 小程序任务页暂不改动
