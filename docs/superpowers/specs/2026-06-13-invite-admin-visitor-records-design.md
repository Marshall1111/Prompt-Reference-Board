# 后台邀请码页访问记录改造设计

## 背景

当前后台 `邀请码` 页面同时承担两类信息：

- 邀请码与匿名免费次数管理
- 访客额度列表

现有下半区展示的是 `访客额度`，每条记录只包含访客身份、提权状态、已用额度、剩余额度和最近更新时间。这套信息对于排查额度问题有帮助，但在日常运营里不够高频，且占用页面空间较大。

当前更重要的管理诉求是快速回答以下问题：

- 最近有哪些访客来过
- 这些访客来自哪个商户
- 他们最近停留了多久
- 他们发起过多少次生成
- 他们累计贡献了多少订单金额

因此，这个页面需要从“额度视角”调整为“访问记录视角”。邀请码管理能力继续保留，但原有的 `访客额度` 列表需要替换成按访客聚合的紧凑型 `访问记录` 列表。

## 目标

本次改造需要满足以下目标：

- 保留后台现有的邀请码创建、启停、历史已用邀请码查看、匿名免费次数设置能力
- 将原 `访客额度` 区块替换为 `访问记录`
- 访问记录按访客聚合，一行代表一个访客
- 列表按最近活跃时间倒序展示
- 每行展示以下字段：
  - 访客
  - 来源商户
  - 最近活跃
  - 最近停留时长
  - 生成次数
  - 订单金额
- 停留时长使用真实访问埋点，不使用纯推算值
- 历史访客在没有访问埋点时，停留时长允许显示 `--`
- 列表样式需要比当前卡片式访客额度列表更紧凑，优先保证信息密度和快速扫读

## 非目标

本次不做以下内容：

- 不移除或重构现有邀请码数据结构
- 不引入数据库，继续沿用当前 JSON 文件存储方式
- 不在首版中加入复杂筛选、导出、图表、访客详情抽屉
- 不回填历史访问停留时长，历史数据只做兼容展示
- 不改变公共页面现有的生成、收藏、下单主流程

## 现状梳理

### 后台邀请码页

当前 `InviteAdminPage` 包含三块内容：

- 匿名访客默认免费次数设置
- 当前可用邀请码列表与历史已用邀请码折叠区
- 访客额度列表

现有 `访客额度列表` 数据来自：

- `GET /api/admin/visitors`

当前返回结构主要包含：

- `visitorId`
- `tier`
- `quotaLimit`
- `quotaUsed`
- `quotaRemaining`
- `sourceMerchantId`
- `sourceMerchantName`
- `createdAt`
- `updatedAt`

### 现有可复用的数据

当前系统中，以下数据已经存在且可复用：

- 访客状态
  - 存在于 `data/visitor-states/*.json`
  - 已包含 `visitorId`、`sourceMerchantId`、`sourceMerchantName`、`createdAt`、`updatedAt`
- 公开任务
  - 任务记录包含 `ownerVisitorId`
  - 可据此统计某个访客发起过多少次公开生成
- 冰箱贴订单
  - 订单记录包含 `visitorId`
  - 订单记录包含 `totalCents`
  - 可据此统计某个访客的累计订单金额

### 当前缺失的数据

当前系统没有真实的访问停留时长埋点，因此缺少以下信息：

- 访客何时进入公开页面
- 页面停留期间是否持续活跃
- 访客何时离开页面
- 一次连续访问持续了多久

如果不新增埋点，`最近停留时长` 只能使用近似值，例如“最近一次生成耗时”或“最近活跃跨度”。这会让 `访问记录` 的语义不准确，因此不采用近似口径作为首选方案。

## 方案概览

采用以下方案：

- 后台 `邀请码` 页保留邀请码管理区块
- 原 `访客额度` 区块替换为 `访问记录`
- 前台公共页面新增访问会话埋点
- 服务端新增访问会话存储与聚合逻辑
- 管理端通过新接口读取按访客聚合后的访问记录

这是本次推荐方案，原因如下：

- 可以保留现有邀请码能力，不打断现有运营流程
- 可以准确支持 `最近停留时长`
- 可以在不引入数据库的前提下，复用现有 JSON 文件存储模式
- 为后续扩展“访客详情”“访问历史”“转化分析”保留原始会话数据

## 访问记录口径

### 聚合粒度

访问记录按 `访客` 聚合。

一行代表一个访客，而不是一条原始访问事件或一段原始访问会话。

### 排序规则

访问记录按 `最近活跃时间` 倒序排列。

### 字段定义

#### 访客

显示短访客 ID，用于快速区分不同访客。

前端展示短 ID，后端仍返回完整 `visitorId`。

#### 来源商户

来源商户沿用访客状态中的：

- `sourceMerchantId`
- `sourceMerchantName`

若访客当前没有有效来源商户，则显示 `无`。

#### 最近活跃

取该访客最近一次访问会话的最新活跃时间，优先级如下：

1. 最近访问会话的 `lastHeartbeatAt`
2. 如果没有心跳，则回退到该会话的 `endedAt`
3. 如果仍然没有，则回退到该会话的 `startedAt`
4. 对于历史无访问会话的访客，回退到现有访客状态的 `updatedAt`

#### 最近停留时长

取该访客最近一次访问会话的 `durationSeconds`。

如果访客没有访问会话埋点，则返回 `null`，前端显示 `--`。

#### 生成次数

统计该访客发起过多少次公开生成会话。

口径按“轮次”计算，而不是按生成结果张数计算。实现上应优先统计公开玩法会话数，而不是统计单张任务数。

#### 订单金额

统计该访客累计订单金额，使用订单的 `totalCents`。

首版口径如下：

- 包含运费
- 累计所有未取消订单
- 已取消订单不计入

## 访问埋点设计

### 目标

新增一套轻量访问会话埋点，用于记录公开页面的连续访问时长。

### 原始记录粒度

原始访问数据按“连续访问会话”存储。

每一条访问会话表示访客进入某个公开页面后，在一段连续活跃时间内的访问行为。

### 存储位置

新增目录：

- `data/visit-sessions/`

每个访问会话存为一个独立 JSON 文件。

### 访问会话结构

建议字段如下：

```json
{
  "sessionId": "uuid",
  "visitorId": "uuid",
  "experienceType": "draw-card",
  "route": "/fridge",
  "sourceMerchantId": "merchant-id",
  "sourceMerchantName": "商户名",
  "startedAt": "2026-06-13T10:00:00.000Z",
  "lastHeartbeatAt": "2026-06-13T10:03:18.000Z",
  "endedAt": "2026-06-13T10:03:20.000Z",
  "durationSeconds": 198,
  "status": "ended"
}
```

其中：

- `status` 取值为：
  - `active`
  - `ended`
  - `timed_out`

### 访客状态补充字段

为了更方便衔接访问会话和访客聚合，可以在 `visitor state` 中补两个轻量字段：

- `lastActiveAt`
- `activeVisitSessionId`

这两个字段只用于提升服务端读写便利性，不承担完整的访问历史职责。

### 前台上报事件

公共页面新增访问上报接口，前端使用同一个接口上报三类事件：

- `enter`
- `heartbeat`
- `leave`

### 前台上报时机

建议如下：

- 页面进入时上报一次 `enter`
- 页面处于前台且活跃时，定时上报 `heartbeat`
- 页面关闭、切后台、刷新、路由离开时，尽量上报一次 `leave`

### 时长计算规则

`durationSeconds` 使用以下规则计算：

- 正常离开时：`endedAt - startedAt`
- 异常关闭或丢失离开事件时：`lastHeartbeatAt - startedAt`

服务端需要支持超时兜底：

- 如果访问会话长时间没有新的心跳，则自动标记为 `timed_out`
- 超时时长口径在实现阶段统一定义，例如 90 秒或 120 秒

### 历史兼容

历史访客不会补写旧访问会话，因此：

- `最近停留时长` 显示 `--`
- `最近活跃时间` 允许退回使用 `visitor.updatedAt`

## 接口设计

### 公共接口

新增接口：

- `POST /api/visit-sessions/report`

#### 请求体

建议请求体如下：

```json
{
  "eventType": "heartbeat",
  "experienceType": "fridge-magnet",
  "route": "/fridge",
  "currentSessionId": "uuid-or-empty"
}
```

### 公共接口行为

#### `enter`

- 创建新的访问会话
- 回写 `sessionId`
- 更新访客状态中的 `lastActiveAt`
- 更新访客状态中的 `activeVisitSessionId`

#### `heartbeat`

- 更新当前访问会话的 `lastHeartbeatAt`
- 更新访客状态中的 `lastActiveAt`

#### `leave`

- 写入 `endedAt`
- 计算 `durationSeconds`
- 将访问会话状态改为 `ended`
- 清理访客状态中的 `activeVisitSessionId`

### 管理端接口

新增接口：

- `GET /api/admin/visitor-records`

该接口返回按访客聚合后的结果，而不是直接返回原始访问会话。

#### 返回字段

建议返回结构如下：

```json
{
  "records": [
    {
      "visitorId": "uuid",
      "sourceMerchantId": "merchant-id",
      "sourceMerchantName": "商户名",
      "lastActiveAt": "2026-06-13T10:03:18.000Z",
      "lastVisitDurationSeconds": 198,
      "generationCount": 4,
      "orderTotalCents": 7960,
      "createdAt": "2026-06-10T08:00:00.000Z",
      "updatedAt": "2026-06-13T10:03:18.000Z"
    }
  ]
}
```

#### 聚合规则

每个访客聚合一条记录，规则如下：

- `sourceMerchantId` / `sourceMerchantName`
  - 优先取访客状态中的当前值
- `lastActiveAt`
  - 取最近访问会话的最近活跃时间
  - 如果没有访问会话，则回退到访客状态 `updatedAt`
- `lastVisitDurationSeconds`
  - 取最近访问会话的 `durationSeconds`
  - 如果没有访问会话，则返回 `null`
- `generationCount`
  - 统计该访客的公开生成会话数
- `orderTotalCents`
  - 统计该访客所有未取消订单的 `totalCents` 累计值
- `createdAt`
  - 取访客状态 `createdAt`
- `updatedAt`
  - 取聚合后的最近更新时间

## 后台页面设计

### 页面定位

后台 `邀请码` 页面保留为一个综合管理页，但信息结构调整为：

1. 邀请码管理
2. 访问记录

页面标题改为：

- `邀请码与访问记录`

页面说明改为：

- 创建邀请码、设置匿名免费次数，并查看最近访客的来源、停留、生成与下单情况。

### 上半区：邀请码管理

保留以下内容：

- 匿名访客默认免费次数设置
- 创建邀请码
- 当前可用邀请码列表
- 历史已用邀请码折叠区

这部分不改数据结构，只做必要的文案与布局收紧。

### 下半区：访问记录

原 `访客额度` 区块整体替换为 `访问记录`。

首版使用紧凑列表，不沿用当前大卡片布局。

#### 列表字段顺序

列表展示字段顺序如下：

- 访客
- 来源商户
- 最近活跃
- 最近停留时长
- 生成次数
- 订单金额

#### 列表样式

桌面端采用单行紧凑列表，每行展示一个访客：

```text
访客        来源商户       最近活跃            最近停留   生成次数   订单金额
8fa3c1d2    小红书-A店     2026-06-13 14:32    3分18秒    4         ¥79.60
2c7ab901    无             2026-06-13 14:20    --         1         ¥0.00
```

窄屏下自动折成两行：

- 第一行：访客 / 来源商户 / 最近活跃
- 第二行：最近停留时长 / 生成次数 / 订单金额

#### 行内显示规则

- 访客：显示短 ID，完整 ID 不直接展示
- 来源商户：没有值时显示 `无`
- 最近停留时长：没有值时显示 `--`
- 订单金额：统一格式化为人民币金额

#### 首版展示条数

首版默认展示最近 50 条访问记录。

如果后续记录数持续增长，再在独立迭代中补充分页或筛选能力。

#### 空状态

当没有任何访问记录时，显示：

- `还没有访问记录。`

## 数据读取与聚合实现建议

### 访问记录聚合入口

管理端访问记录接口需要聚合以下三类数据：

- 访客状态
- 访问会话
- 订单

如果实现上需要降低复杂度，可以将“生成次数”从公开生成会话中读取，而不是从原始任务逐条推断。这样更符合“按轮次统计”的口径。

### 性能考虑

首版继续使用文件扫描聚合即可，不做预计算缓存。

原因如下：

- 当前项目整体仍是本地或轻量部署场景
- 访问记录页的使用频率低于公开页面
- 首版只展示最近 50 条记录，数据规模可控

若后续访客量、任务量、订单量显著增长，再新增聚合缓存或索引层。

## 兼容与迁移

本次不做历史数据迁移。

兼容规则如下：

- 历史访客没有访问会话时：
  - `lastVisitDurationSeconds = null`
  - 页面显示 `--`
- 历史访客仍可显示：
  - 访客
  - 来源商户
  - 最近活跃
  - 生成次数
  - 订单金额

这样可以保证功能上线后立刻可用，同时允许访问时长逐步随着新埋点积累起来。

## 测试与验收

### 服务端

需要覆盖以下场景：

- `enter` 能创建访问会话并返回 `sessionId`
- `heartbeat` 能更新访问会话的 `lastHeartbeatAt`
- `leave` 能正确结束会话并写入 `durationSeconds`
- 丢失 `leave` 时会话能被超时收口为 `timed_out`
- 管理端访问记录接口能正确聚合来源商户、最近活跃、最近停留、生成次数、订单金额
- 已取消订单不会计入订单金额

### 前端

需要覆盖以下场景：

- 后台 `邀请码` 页标题与说明文案更新正确
- 原 `访客额度` 区块消失
- 新 `访问记录` 列表展示正确
- 历史无访问埋点时正确显示 `--`
- 窄屏下列表能折成两行且仍可读

### 验收标准

当管理员进入后台 `邀请码` 页面时，应能在同一页面里完成两件事：

- 管理邀请码和匿名免费次数
- 快速查看最近访客的来源商户、停留时长、生成次数和订单金额

并且页面不再突出展示 `访客额度` 明细。

## 风险与取舍

### 风险一：前端离开事件不可靠

浏览器关闭、刷新、切后台时，`leave` 事件不一定总能成功发送。

应对方式：

- 使用心跳机制作为主要时长依据
- 使用超时关闭作为服务端兜底

### 风险二：按任务数统计会偏离“轮次”语义

如果直接按任务条数统计，可能与用户理解中的“发起过几次生成”不一致。

应对方式：

- 明确按公开生成会话数统计 `generationCount`

### 风险三：访问记录页后续可能继续膨胀

如果未来又追加筛选、导出、图表、详情抽屉，这个页面可能再次变重。

应对方式：

- 首版只保留核心列表
- 后续扩展放到单独迭代中处理

## 推荐实施顺序

建议按以下顺序实现：

1. 新增访问会话存储结构与读写工具
2. 新增 `POST /api/visit-sessions/report`
3. 在公开页面接入 `enter` / `heartbeat` / `leave`
4. 新增 `GET /api/admin/visitor-records`
5. 将后台 `邀请码` 页的 `访客额度` 区块替换为 `访问记录`
6. 调整后台样式为紧凑列表
7. 补充服务端与前端验证

## 结论

本次改造不应只做“把访客额度文案改成访问记录”，而应补上一套真实访问会话埋点，再在后台按访客聚合展示运营真正关心的数据。

最终结果是：

- 邀请码管理继续保留
- 访客额度列表退出主界面
- 后台获得更贴近运营视角的访问记录页
- 停留时长、生成次数、订单金额形成一套可持续扩展的数据基础
