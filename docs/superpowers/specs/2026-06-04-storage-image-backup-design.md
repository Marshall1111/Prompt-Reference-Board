# 存储图片备份导出设计

## 背景

当前后台已经具备基础的存储管理能力，包括：

- 查看任务相关目录的空间占用
- 创建轻量级配置备份
- 下载和删除备份文件
- 按保留天数清理历史数据

但现有备份只覆盖风格、分组、邀请码和系统设置这类 JSON 配置，不包含服务器上最占空间、也最有价值的图片数据。用户希望在清理服务器历史数据前，先将指定日期范围内的图片导出为可下载的压缩包，用于离线保存和后续查找。

## 目标

新增一个按日期范围导出图片备份的后台能力，满足以下目标：

- 管理员可以在后台选择开始日期和结束日期
- 系统导出该范围内的高清原图和临时参考图
- 导出结果整理为按日期分组的目录结构
- 生成可下载的 zip 压缩包
- 压缩包名称使用所选日期范围，例如 `20260601-20260603.zip`
- 压缩包内包含 `manifest.json`，方便之后查找和恢复
- 生成后的压缩包保存在服务器备份目录中，并支持后台下载与删除

## 非目标

本次不做以下内容：

- 不将公开预览图、缩略图、访客额度 JSON、邀请码 JSON 纳入图片备份包
- 不做自动定时归档
- 不做导出后自动清理
- 不做从备份包一键恢复数据
- 不改动现有轻量级配置备份的行为

## 用户体验

在 `/admin/storage` 新增“按日期范围导出图片备份”区域，包含：

- 开始日期输入
- 结束日期输入
- “生成备份”按钮
- 导出说明文案

点击“生成备份”后，服务端执行导出并在成功后：

- 将生成的 zip 备份写入服务器备份目录
- 在后台备份列表中新增一条记录
- 管理员可直接下载或删除该备份

如果日期输入不合法，前端应阻止提交并提示：

- 开始日期不能为空
- 结束日期不能为空
- 开始日期不能晚于结束日期

如果选定范围内没有图片可导出，接口返回明确提示，不生成空压缩包。

## 导出范围

导出对象仅包含以下两类文件：

1. 高清原图
2. 临时参考图

### 高清原图来源

从 `data/private-generated-images` 中读取图片文件，并通过对应任务记录关联到生成时间与任务信息。

### 临时参考图来源

从 `data/temp-image-references` 中读取临时参考图目录和文件。

## 日期判定规则

### 高清原图

按对应任务的 `createdAt` 归档。

即：

- 先读取 `data/image-jobs/*.json`
- 找到任务结果所对应的原图文件
- 用该任务的 `createdAt` 作为该图片所属日期

### 临时参考图

优先按临时参考图元数据中的创建时间归档。

如果元数据中缺少明确时间，则回退到目录或文件的文件系统创建时间 / 修改时间。

### 日期筛选

按自然日闭区间处理。

例如选择：

- 开始日期：`2026-06-01`
- 结束日期：`2026-06-03`

则导出范围为：

- `2026-06-01 00:00:00`
- 到 `2026-06-03 23:59:59.999`

### 时区

统一使用服务器本地时区进行日期换算。

这样后台选择的日期与服务器实际导出的结果保持一致。

## 压缩包名称

压缩包名称使用用户选择的日期范围：

- `YYYYMMDD-YYYYMMDD.zip`

示例：

- `20260601-20260603.zip`

如果未来允许只选单日，仍保持同一格式：

- `20260601-20260601.zip`

## 压缩包内部目录结构

采用“按日期分文件夹，再按类型分子目录”的结构。

示例：

```text
2026-06-01/
  originals/
    3915d417-5285-436b-8ee1-3b4fa91e95ba.png
  temp-references/
    03521c74-e861-44ba-bae7-d055bd5c2ac3/
      reference-1.png
2026-06-02/
  originals/
    861e4a83-6160-4f53-9021-d19f66627bad.png
  temp-references/
    4039cbb2-0fe2-4b71-adaf-112335b0e1c7/
      reference-1.png
manifest.json
```

说明：

- `originals/` 下放高清原图
- `temp-references/` 下放临时参考图
- 对于一组临时参考图，保留其原有参考目录分组，避免文件名冲突
- 压缩包根目录额外附带 `manifest.json`

## manifest.json

压缩包内必须包含 `manifest.json`，用于记录导出内容及其来源。

建议结构：

```json
{
  "version": 1,
  "dateRange": {
    "startDate": "2026-06-01",
    "endDate": "2026-06-03"
  },
  "generatedAt": "2026-06-04T13:20:00.000+08:00",
  "timezone": "Asia/Shanghai",
  "items": [
    {
      "type": "original",
      "date": "2026-06-01",
      "jobId": "3915d417-5285-436b-8ee1-3b4fa91e95ba",
      "sourcePath": "data/private-generated-images/3915d417-5285-436b-8ee1-3b4fa91e95ba.png",
      "archivePath": "2026-06-01/originals/3915d417-5285-436b-8ee1-3b4fa91e95ba.png",
      "createdAt": "2026-06-01T10:00:00.000+08:00"
    },
    {
      "type": "temp-reference",
      "date": "2026-06-01",
      "referenceId": "03521c74-e861-44ba-bae7-d055bd5c2ac3",
      "sourcePath": "data/temp-image-references/03521c74-e861-44ba-bae7-d055bd5c2ac3/reference-1.png",
      "archivePath": "2026-06-01/temp-references/03521c74-e861-44ba-bae7-d055bd5c2ac3/reference-1.png",
      "createdAt": "2026-06-01T09:30:00.000+08:00"
    }
  ]
}
```

至少记录以下字段：

- 文件类型
- 所属日期
- 任务 ID 或参考图 ID
- 原始相对路径
- 压缩包内路径
- 关联时间

## 服务端实现方案

后台体验是“生成备份并下载”，但服务端内部采用“两阶段实现”：

1. 先生成临时导出目录
2. 再将临时导出目录压缩为 zip

这样做的原因：

- 更容易排查导出失败问题
- 更容易验证目录结构是否正确
- 后续可以扩展为“导出后自动清理”而不重写整条链路

### 阶段一：构建临时导出目录

服务端根据日期范围收集文件，并在临时目录中构建最终目录结构：

- `YYYY-MM-DD/originals/*`
- `YYYY-MM-DD/temp-references/*`
- `manifest.json`

### 阶段二：打包 zip

将临时导出目录压缩为 zip 文件，并保存到服务器备份目录。

## 备份目录管理

图片 zip 备份仍保存在现有服务器备份目录中，但需要在元数据中区分类型：

- `config-snapshot`
- `image-range-zip`

后台备份列表应能展示：

- 备份类型
- 日期范围
- 文件名
- 创建时间
- 文件大小

## 后端接口设计

### 新增接口

`POST /api/admin/storage/image-backups`

请求体：

```json
{
  "startDate": "2026-06-01",
  "endDate": "2026-06-03"
}
```

行为：

- 校验管理员登录态
- 校验日期格式与范围
- 收集范围内的高清原图和临时参考图
- 生成压缩包和 manifest
- 将备份记录写入服务器备份目录
- 返回备份元数据

### 复用现有接口

现有下载与删除接口继续使用，但需要兼容新的图片 zip 备份类型：

- `GET /api/admin/storage/backups/:backupId/download`
- `DELETE /api/admin/storage/backups/:backupId`

## 错误处理

### 输入错误

- 日期缺失：返回 400
- 日期格式无效：返回 400
- 开始日期晚于结束日期：返回 400

### 业务错误

- 范围内无图片可导出：返回 400，并提示“所选日期范围内没有可备份图片”

### 系统错误

- 临时目录构建失败：返回 500
- zip 生成失败：返回 500
- 备份文件写入失败：返回 500

所有失败路径都需要清理中间临时目录，避免服务器残留垃圾文件。

## 兼容性与迁移

- 现有轻量级配置备份继续保留，不做破坏性修改
- 现有备份列表需要兼容展示新旧两种备份
- 现有下载 / 删除逻辑要继续适配旧备份文件
- 已存在的 `.json` 配置备份不能因新增 zip 备份而不可下载

## 测试计划

### 日期校验

- 开始日期为空时报错
- 结束日期为空时报错
- 开始日期晚于结束日期时报错

### 导出成功

- 选择有图片数据的日期范围后成功生成 zip
- 文件名符合 `YYYYMMDD-YYYYMMDD.zip`
- zip 内目录结构符合约定
- zip 内包含 `manifest.json`

### 内容正确性

- 高清原图按任务 `createdAt` 归档到正确日期目录
- 临时参考图按元数据 / 文件时间归档到正确日期目录
- manifest 中记录的 `archivePath` 与实际压缩包内容一致

### 后台操作

- 新生成的 zip 备份可下载
- 新生成的 zip 备份可删除
- 旧的 JSON 配置备份仍可下载和删除

### 空结果

- 所选日期范围内无图片时，不生成空包并返回明确提示

## 推荐实现顺序

1. 扩展备份元数据模型，区分配置备份与图片 zip 备份
2. 实现日期范围校验和候选文件收集
3. 实现临时导出目录构建与 manifest 生成
4. 实现 zip 打包
5. 扩展后台 `/admin/storage` 页面
6. 验证新旧备份下载与删除兼容性
